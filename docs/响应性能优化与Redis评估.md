# 响应性能优化与 Redis 评估

日期：2026-09-23。范围：课程检索、云盘目录加载与缓存选型。本轮不新增 Redis 服务，不改数据库结构，不操作业务文件。

2026-10-09 更新：项目已新增独立可选的 Redis 存储源展示元数据缓存，并修复后台导航重复请求及存储列表持续加载问题。启用方式、一致性与测试边界见 [后台导航优化与Redis缓存说明](后台导航优化与Redis缓存说明.md)。下文“不启用 Redis”的结论仅代表 2026-09-23 那轮工作，不再代表当前所有功能。

2026-09-25 后续优化另见 [业务响应优化说明](业务响应优化说明.md)：目录按页传输、PDF 单页渲染、真实流式对话及后台任务。本页以下数据保留为此前检索优化的独立测量，不混作本轮全站性能指标。

## 已完成的优化

### 课程检索减少无用磁盘读取

原实现每次搜索都会重新读取本人所有索引文件，之后才判断是否匹配关键词。30 份、每份 5 MiB 时，一次搜索最多读取约 150 MiB，即使最终没有任何命中也是如此。

现实现先在当前用户自己的索引文本上排序，再依次验证候选资料，获得 5 个有效片段后停止。无关键词命中的资料不读取原文件。同一文件在多个课程／片段中重复出现时，同一次请求只计算一次指纹。

安全约束保持不变：返回片段前重新检查用户权限、根目录、隐藏／密码规则、文件存在性，并完整计算 SHA-256。没有采用“大小与修改时间没变就跳过校验”的方法，也没有跨请求缓存权限或指纹。校验改为 8 KiB 缓冲区流式读取，避免搜索时为每个文件分配最大 5 MiB 的数组。

`skipped` 的含义调整为“本次已检查但失效的候选资料数”，页面已同步说明；它不是全库健康检查。高排名候选失效时继续补足后面的有效结果，最坏情况仍可能读取全部 30 份资料。

### 目录加载并行化及旧请求取消

用户根目录用于匹配已保存的目录密码，因此仍需先读取。之后文件列表与目录配置改为并行请求，不再等待文件列表返回后才请求配置。配置较慢时，文件列表可以先展示；新的权限配置到达前保持操作权限为空。

快速切换目录、存储源或排序时取消旧请求，旧文件列表、目录权限、用户根路径及错误响应均不能覆盖新状态。离开页面时也取消请求。网络失败、超时后正确结束加载状态；目录查询单次超时为 30 秒，不影响大文件上传／下载的超时设置。

取消浏览器请求主要减少无效等待、传输和旧状态覆盖，并不保证已经执行的远端存储扫描也会立即停止。

## 本地性能对比

测试使用临时合成文件，不读取真实用户资料。Windows、Java 21；30 份文件，每份 5 MiB，各含一个相同分数的匹配片段，目标返回 5 个片段。先预热 2 轮，再取 7 轮中位数；操作系统文件缓存已预热。

| 指标 | 原校验策略 | 新候选校验策略 |
| --- | ---: | ---: |
| 单次读取文件数 | 30 | 5 |
| 单次读取数据量 | 150 MiB | 25 MiB |
| 第一轮中位耗时 | 163.70 ms | 27.83 ms |
| 完整回归时再次测量 | 174.20 ms | 27.53 ms |

这些数字只测量本地文件读取／指纹校验路径，新策略还包含内存候选排序；未包含数据库、鉴权、HTTP、前端渲染或真实模型请求。不应解释为整个系统提速相同比例。不同硬盘、文件分布、命中率和并发量会改变结果。

复测（项目根目录，JDK 21、Maven 已加入 PATH）：

```powershell
mvn -B -f backend/pom.xml '-Dtest=LearningSearchTest' '-Dlearning.benchmark=true' test
```

基准默认关闭，普通 CI 只执行功能断言，不用不稳定的墙钟阈值作为通过条件。

## 是否需要 Redis

**当前建议：不为这轮优化强制启用 Redis。保留已有可选接入，先消除无用工作。**

代码中已经存在：

- `spring-boot-starter-data-redis` 依赖。
- 由 `spring.data.redis.host` 激活的 Sa-Token Redis 会话实现。
- 默认开启的 Spring 内存缓存，缓存配置和用户存储权限等数据。
- 单独使用进程内 `ConcurrentHashMap` 的用户可用存储源列表缓存。

因此项目不是“没有缓存”。把已有进程内命中改成网络 Redis 访问，不一定更快。Redis 也不能直接消除文件全文哈希、外部模型推理或多个串行 HTTP 往返的成本。

适合进一步接入 Redis 的条件：确实需要多个后端实例共享登录会话、跨实例限流，或实测出现大量重复数据库读取且本地缓存不能满足一致性。不能只根据用户总数决定；应比较实际流量下的命中率、数据库耗时、接口 P50／P95 和错误率。

在多实例部署前还需统一现有进程内缓存的失效机制：仅填写 Redis 地址，不会把独立的 `ConcurrentHashMap`、存储服务实例及所有限流逻辑自动变成分布式。否则某实例修改权限，另一实例可能仍保留旧状态。

若后续正式启用，应先在隔离环境验证：

1. 缓存键按应用／环境及必要的账号、存储源维度隔离。
2. 事务提交后失效，覆盖修改权限、禁用账号、隐藏文件、删除存储源等操作；验证各实例立即正确响应。
3. 认证／权限数据在 Redis 故障时不能按“允许访问”降级；普通非安全配置可以设计回源。
4. 设置内存上限、TTL、连接超时和访问控制，禁止公网裸露；验证会话淘汰和重启行为。
5. 不把私有资料检索结果或 Agent 回答仅按问题文本做共享缓存，以免跨账号返回资料；缓存命中也不能绕过当前授权校验。

选型参考：[Spring Boot 缓存说明](https://docs.spring.io/spring-boot/reference/io/caching.html)、[Redis 缓存一致性与失效说明](https://redis.io/docs/latest/develop/clients/client-side-caching/)。这只是设计参考，不代表本轮已验证 Redis 部署或多实例一致性。

## 测试记录与边界

- 后端完整回归与 JAR 打包：62 项通过，0 失败、0 跳过（显式启用了上述基准）。包含真实临时数据库 HTTP 工作流、同大小同时间文件覆盖、权限撤销、密码父目录与文件删除。
- 新增检索测试：无命中不读原文件、前 5 命中提前停止、失效候选替补、同一文件请求内去重、下次请求重新校验、流式哈希与大小边界。
- 前端单元测试：17 项通过。新增请求取消、旧结果抛弃、并行加载、配置较慢时先展示列表、网络／配置错误等场景。
- 前端类型检查、改动范围 ESLint（0 错误／0 警告）和最终生产构建均通过。生产构建仍提示部分预览模块超过 500 kB 及历史 Sass 弃用警告，不把构建通过等同于首屏或浏览器性能验收。
- 真实外部模型服务耗时、真实浏览器点击与目标服务器并发压测不在上述基准范围内，未将代码测试冒充这些实测。

模型响应慢需要另行区分上游耗时、工具调用轮数、检索耗时和首段输出时间。此次检索优化会减少 Agent 调用课程工具时的本地工作，但不能据此声称模型生成本身更快。
