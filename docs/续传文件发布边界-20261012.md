# 续传文件发布边界

续传完成操作先持久化 `COMPLETING`，再使用 `CREATE_NEW + WRITE + NOFOLLOW_LINKS` 创建目标文件，并通过同一个输出句柄以 8 KiB 缓冲复制已组装文件。复制长度必须与会话声明长度一致，输出句柄成功关闭后才可以记录 `COMPLETED`。

`CREATE_NEW` 的存在检查与创建相对其他文件系统操作是原子的；同名文件或符号链接已经存在时，发布会失败，不会将其打开以写入。依据：[Java 21 Files.newByteChannel 契约](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/file/Files.html#newByteChannel(java.nio.file.Path,java.util.Set,java.nio.file.attribute.FileAttribute...))。

目标文件的完整内容不是一次性原子可见的：复制过程中，目录浏览或下载可能看到空文件或部分内容。复制、关闭句柄或记录完成回执出现异常后，会话保持 `COMPLETING`，目标文件与暂存资料供人工核查；系统不会自动重复发布，也不会为回滚删除目标路径。清理续传暂存任务不会删除云盘目标文件。应先人工核查目标文件，再决定是否另行上传。

服务器需要承担一次额外的整文件读取和写入。复制期间，暂存分片、组装文件和云盘目标可能同时占用磁盘；私有暂存配额仍只覆盖分片与组装文件的两倍长度，云盘卷还需要容纳目标文件。暂存卷与云盘卷共用物理磁盘时，应为这份额外复制预留空间。大文件的完成操作时间也会增加。

不能仅依据 `Files.move` 未传 `REPLACE_EXISTING`，就声称 Linux 同一文件系统下绝不会覆盖竞争创建的目标。官方 OpenJDK 21u 实现先检查目标属性，再执行普通 `rename`；Linux `rename` 会替换在调用时已存在的目标，两个动作之间存在竞争窗口。依据：[OpenJDK UnixFileSystem.move](https://github.com/openjdk/jdk21u/blob/master/src/java.base/unix/classes/sun/nio/fs/UnixFileSystem.java#L847)、[JNI rename 实现](https://github.com/openjdk/jdk21u/blob/master/src/java.base/unix/native/libnio/fs/UnixNativeDispatcher.c#L1044)、[Linux rename 文档](https://github.com/mkerrisk/man-pages/blob/master/man2/rename.2#L79)。

该保证针对本次发布不会覆盖已经存在的目标；它不防止其他有权写入云盘的操作在发布过程中或之后移动、替换、删除目标。主服务仍需执行当前权限、根目录身份、路径与复制后授权复核。
