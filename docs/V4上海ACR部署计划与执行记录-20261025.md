## 与原计划的必要适配

| 原计划或实际差异 | 本次采用的做法 | 原因 |
| --- | --- | --- |
| 简化旧 Nginx 路由 | 使用当前 `routes.conf` / `proxy.conf` 及完整 http 层定义 | 保留客服 WebSocket、AI SSE、续传分片限制、内部探针隐藏和代理头校验 |
| 前端既本地构建，又在 Docker 中构建 | 新增 `frontend/Dockerfile.acr`，只复制同一份本地 `dist` 和 Nginx 配置 | 服务器 index.html SHA256 必须与本地一致；不覆盖原有通用多阶段 Dockerfile |
| 默认忽略 dist 的 Docker 上下文 | 发布脚本创建只含 dist、三份 Nginx 配置及 Dockerfile 的临时上下文 | 避免 COPY 失败，也不把本地配置或密钥带入镜像 |
| 容器内监听 80/443 | 沿用当前镜像 HTTP 8080、TLS 8443 | 与现有健康检查一致；只调整宿主机映射 |
| 转发头策略 framework | 保持 `none`，只信任 V4 Nginx 的 `172.21.0.10/32` | 配合源码的真实 socket peer 与可信代理边界 |
| 只有 /data 持久化 | 另外持久化 `/app/upload-staging`，UID 10001、权限 700 | 避免重建丢失续传，且暂存不进入可浏览存储根 |
| backend 只检查 Up | 使用内置 `/internal/ready`，web 等待 backend healthy | 检查数据库实际连接，不能仅凭进程存在上线 |
| Java 堆上限 1 GiB | V4 Java 堆上限 512 MiB，容器 896 MiB；MySQL 640 MiB、web 128 MiB | 服务器总内存约 3.5 GiB，并行保留两套旧环境；启动后继续观察 OOM 和余量 |
| 计划称上海 JRE 镜像已存在 | 检查发现缺失，从本机既有 IBM JRE 缓存同步到同一上海 ACR 路径 | 避免构建依赖 Docker Hub；不改变后端业务代码 |
| AI / SMTP 凭据 | 测试阶段均关闭，数据库与验证码秘密新生成 | 不自动复用聊天记录或第三版秘密，后续需要时交由用户安全输入 |

V4 使用 `172.21.0.0/24` 独立网络。检查时它与服务器已有 Docker 网络和 VPC 路由无冲突，创建前仍会复核。

## 执行顺序与检查点

1. 检查本机 Docker Client/Server、项目目录、Git 状态与 `baseUrl=""`。Docker Engine 不可用时等待用户启动。
2. 用现有 credential store 验证上海 ACR；缺少凭据或认证失败时停止，要求用户在隐藏提示中执行 `docker login`。不记录密码。
3. 验证基础镜像，构建 linux/amd64 后端；检查镜像 ID 后推送并核对实际 digest。
4. 在前端目录使用其固定的 pnpm 版本，依次 frozen install、typecheck、build。任一步失败均先停止分析。
5. 记录本地 `dist/index.html` SHA256，用同一 dist 构建前端镜像，推送并核对 digest。
6. 发布清单记录 commit、未提交状态摘要、构建输入指纹、镜像 digest 和前端 SHA；不会伪称构建来自干净 commit。
7. 复核服务器 V4 卷不存在。若卷已存在，停止并请求用户处理，绝不自动删除。
8. 上传无秘密的 V4 配置 bundle，在服务器生成新的两个数据库密码与验证码 secret，直接写入权限 600 的专用 `.env`，不回显。
9. 仅从 ACR 拉取镜像，校验与本地清单的 digest 一致。Compose 只以 `config -q` 校验，不输出展开的秘密。
10. 启动独立 V4，检查 MySQL/backend/web healthy、Nginx 语法、完整 Flyway 迁移、新库未安装状态、前端 SHA256 及服务器资源余量。
11. **暂停，等待用户通过 SSH 隧道手动完成 `/install`。不自动设置或记录全局管理员密码。**
12. 用户确认安装完成后，验证登录、权限隔离、后台、空间、上传/下载/分享及新增功能。AI/邮件若未配置，报告为未启用，不能写成测试通过。
13. 复制服务器既有域名证书到 V4，保留证书链目录和权限，不重新申请证书、不下载私钥到本机。验证 Nginx TLS 配置。
14. 准备正式 origin 与 80/443 映射，避免提前破坏仍用于验收的测试入口。
15. **再次暂停：明确请求用户确认正式接管域名及 80/443。收到明确“继续”后才能切换。**
16. 只停止 V3 web，核实端口释放，再创建 V4 正式 web；不停止 V3 数据库或删除旧环境。
17. 验证 HTTP 跳转、HTTPS 证书、API、实际镜像与 SHA。若正式切换严重异常，停止 V4 web、恢复 V3 web，保留双方数据库与文件。
