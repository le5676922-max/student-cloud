# 当前功能完成后的业务优化顺序

以下是后续扩展建议，不代表这些功能已实现，也不替代本轮验收清单。

| 顺序 | 业务问题 | 建议做法 | 验收重点 |
| --- | --- | --- | --- |
| 1 | 管理员离开后空间或课程无人维护 | 空间管理员交接、课程创建者转交、离职冻结与个人资料导出 | 交接需双方确认，原管理员权限及时撤回，不把私人目录整体交给接任者 |
| 2 | 文件误删和覆盖难以恢复 | 回收站、覆盖版本、保留时间、恢复前重名检查 | 恢复仍校验目录和容量；外部云盘不支持版本时明确区分能力 |
| 3 | 大目录实时统计影响上传速度 | 容量预留账本、对象变更记录、后台增量扫描与定期校准 | 并发不会超额；第三方手工变更可检测；未知状态不按零计算 |
| 4 | 多人同时操作或网络重试造成重复执行 | 文件操作幂等标识、可核对的操作收据、异常任务恢复流程 | 超时后可查询实际结果；不盲目重试删除、覆盖、移动 |
| 5 | 共享课程资料难以维护更新 | 资料版本、课程归档、过期资料标记、自动解析与增量知识索引 | 新旧版本可追溯；退出课程立即失去后续检索权限；删除文件后索引不残留 |
| 6 | 用户不知道申请是否已处理 | 站内通知、未读状态、审批原因、客服离线提示 | 通知失败不回滚审批；重复通知去重；只通知相关账号 |
| 7 | 知识库条目越多却答得更差 | 固定评测问题集、引用准确率、召回率、未解决率和发布前后对比 | 正确率数据真实；低质量条目可撤回；评测资料按空间／课程隔离 |
| 8 | 资源使用增长但缺少容量规划依据 | API 分位响应时间、连接池等待、错误率、磁盘余量、AI 调用预算 | 用实际压测确定瓶颈，不用主观人数估算代替测量 |
| 9 | 多实例后缓存、登录和实时通知不一致 | 统一会话存储、共享限流、缓存失效事件、人工客服消息分发 | Redis 只在已明确的共享状态场景使用；故障时权限校验不能降级放行 |

建议先做前四项，再做课程索引和通知。现阶段先保证权限、文件、容量和操作收据一致，再按实际响应时间决定缓存、数据库索引或异步任务的优化顺序。界面继续保持现有主题，只增加与业务状态有关的反馈和入口。
